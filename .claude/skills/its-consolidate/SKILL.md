# its-consolidate: 整理工程

## この工程の役割

開発サイクルの締め。**`design.md` と `todos.md` を実際のソースコードと突き合わせて整える**整頓工程。
新しい設計判断や実装を生む工程ではなく、横断的に見て**ファイルと実装の齟齬をなくす**ことに集中する。
重厚長大な考慮は不要だが、design.md がソースと乖離したまま放置されると以後の局所作業で全体観を失うため、こまめな整頓に価値がある。

## 進め方

### 1. 現状を突き合わせる

- `design.md`・`todos.md` と、実際の `src/`（および `tests/`）を読み比べる。`git log` / 直近の `logs/<タスクID>_*.result.md` の「設計との乖離・補足」も手掛かりにする。
- review 工程からの引き継ぎ（乖離・指摘）があればそれを起点にする。

### 2. todos.md を片付ける

- 実装・テストが済んだタスクに**チェックを付ける**（付け忘れを拾う）。完了済みで役目を終えた記述を整理する。
- Phase の進行に伴い不要・陳腐化した記述、重複を取り除く。残すタスクの依存関係が今も正しいか確認する。
- 冒頭の「**直近の状況**」を最新化する: 直近で完了した内容、現在の到達点、次の着手点を簡潔に。

### 3. design.md をコードに合わせる

- 実装で確定した構造・命名・シグネチャに合わせて design.md を更新する。簡易実装・保留（例: 後続 Phase で差し替え予定の箇所）は、その旨が分かるよう注記する。
- ルールと食い違う記述があれば `docs/rule.md` を正典として設計側を直す。
- アーキテクチャレベルの確定があれば `decisions.md` に反映、解決済みの論点は `tbd.md` から落とす（または解決済みと明記する）。

### 4. 越境しない

- consolidate は整頓であって再設計ではない。新たな設計判断や仕様の決定が必要だと分かったら、その場で決め込まず **design 工程（`its-design`）や `tbd.md` へ送る**。判断が要る論点は指示者に上げる。

### 5. 作業記録を残す

タスクIDがあれば `logs/<タスクID>_<slug>.result.md` に、整理した内容（チェックを付けたタスク、design.md の更新点、解消した乖離、design / tbd へ送った論点）を記録する。
冒頭に実施日時・使用モデルを書く（共通規約は `its-design` の SKILL.md 末尾参照）。
