# its-design: 設計工程

## この工程の役割

AGENTS.md の開発サイクル「design → implement → review → consolidate」の先頭。
与えられた目標（しばしば Phase 単位）に対して **`design.md`（設計）** と **`todos.md`（作業リスト）** を整え、
必要なら **`tbd.md`（指示者が判断すべき論点）** と **`decisions.md`（確定したアーキテクチャ決定）** を更新する。

この工程の最大の価値は、後段の **implement を担う軽量モデルが「早期停止ポリシー」で止まらずに作業できる**よう、
`todos.md` の各タスクを具体的に書き切ることにある。ここはサイクル中で最もコストをかけてよい工程（design > review > implement）。
implement の手戻りを防ぐための先行投資は歓迎される。

## 進め方

### 1. 文脈を読む

新しく読むべき主な資料（既にコンテキストにあるものは再読不要）:

- ルールの正典 **`docs/rule.md`**、世界観 `docs/story.md`、技術前提 `docs/system.md`
- 既存の **`design.md`**（目標設計）、**`todos.md`**（作業リストと冒頭の「直近の状況」）
- 確定決定 **`decisions.md`**（D-xx）、未決論点 **`tbd.md`**（T-xx / G-xx）
- 共有参照 `docs/hex-reference.md`（hex 式の正典）・`docs/types-reference.md`（型・定数の正典）
- 必要に応じて実コード（`src/`）。**設計サイクルの開始・終了時は design.md とソースを突き合わせて乖離を解消する**

### 2. 設計を起こす / 更新する（design.md）

- 目標・スコープ・含める/あえて外すものを明確化する。MVP では「最小ループが成立すれば合格」のように合否基準を言語化する。
- ルールと設計が食い違う場合は **`docs/rule.md` を優先**し、設計側を直す。
- アーキテクチャレベルの判断をしたら `decisions.md` に軽量 ADR（背景 / 決定 / 根拠 / 影響）で追記する。

### 3. 作業リストに分解する（todos.md）— この工程の主眼

各タスクは既存 todos.md の様式 **対象 / API / 要点 / テスト / 完了 / 参照** で書く。軽量モデルが迷わないよう:

- **API のシグネチャと、参照先の式・型をそのまま実装できる**形で書く。座標キーは `key()/parseKey()`、定数は `types-reference §5` を指す等、参照を明示する。
- 関数本体の細部は**擬似コード**で補う。1 タスクあたり関数実装部を除いて**数行〜十数行**まで（全実装を書き込まない／自己防衛的に詳細を盛りすぎない）。
- Phase 間・タスク間の依存（並行作業時の事故防止）と、決定性の規律（乱数は注入 `SeededRng` のみ、タイブレークは `id` 昇順 → `HEX_DIRECTIONS` の index 順 等）を明記する。
- 冒頭の「直近の状況」に、今回の更新内容と次の着手点を1〜数行で残す。

### 4. 未決事項を指示者に上げる（tbd.md）

- 設計の前提を一意に決められない論点は `tbd.md` に論点として記す。当座の開発に重大影響がなければ「暫定案」を併記して進行可能にする。
- **重大影響がある（≒着手前に指示者確認が望ましい）論点は、作業を続ける前にユーザーへ明示的に確認する**（早期停止寄りの判断）。

### 5. implement 可能性の検証（推奨）

todos.md の記述だけで軽量モデルが実装できるか不安なタスクがあれば、**軽量モデル（例: Haiku）のサブエージェントを起動して「この記述で実装可能か／コーナーケースを再現できるか」を判定**させ、不足を todos.md に補う。
ここでの追加コストは後段の効率のため許容される。サブエージェントは**ユーザーが明示的に求めた場合、または記述の実装可能性に具体的な不安がある場合**に使う（無条件には起動しない）。

### 6. 作業記録を残す

タスクID（`YYYYMMDD_NNN`）が与えられていれば（または規約に従い採番できれば）、`logs/<タスクID>_<slug>.result.md` に記録する。
詳細は本ファイル末尾「作業記録の共通規約」を参照。次工程は通常 `its-implement`。

## 作業記録の共通規約（design/implement/review/consolidate 共通）

- タスクID `YYYYMMDD_NNN`: 指示で与えられればそれを使う。未指定なら `docs/record-guideline.md` の規約で当日の連番（`logs/` の既存最大連番+1、001 始まり）を採番する。
- 記録は `logs/<タスクID>_<可読slug>.result.md`。冒頭に**実施日時と使用モデル**を記す。
- 一つのタスクIDに連続指示が来たら、同じ result.md に追記していく。
- 指示が `logs/<タスクID>_*.request.md` で与えられた場合はそれに対応する result を書く。直接指示なら result のみでよい。
