# its-review: レビュー工程

## この工程の役割

implement の成果を、**design 時の考慮とプロジェクト全体の指針に照らして適正か確認する**工程。
コストは design > review > implement の中間で、implement より一段広い視野で見る。
原則として**指摘を返す工程**であり、コード修正そのものは行わない（ユーザーが修正まで求めた場合を除く）。

## 何と照らすか（観点の正典）

- **`docs/rule.md`**（ゲーム仕様の一次定義）— 勝敗・ターン進行・移動・戦闘・資源/建造の意味論が守られているか。設計とルールが食い違えば rule.md が優先。
- **`design.md`** — 設計意図・層構成（domain / application / infrastructure / presentation、依存は内向き）どおりか。presentation が `GameService` だけに依存しているか、domain が純粋関数で副作用なしか。
- **`decisions.md`（D-xx）** — 確定決定に反していないか。特に決定性の規律（D-11: 乱数は注入 `SeededRng` のみ、生成リトライは同一ストリーム継続、タイブレークは `id` 昇順 →`HEX_DIRECTIONS` index 順）。
- **`todos.md` の「完了」条件** — 各タスクが自身の完了条件・テスト欄を満たしているか。カバレッジ閾値（80% / D-10）。
- 共有参照 `docs/hex-reference.md` / `docs/types-reference.md` — 式・型・定数を正典どおり使っているか（座標キーは `key()/parseKey()`、定数は `types-reference §5`）。

## 進め方

### 1. スコープを決める

レビュー対象（Phase / タスク / 差分）と**タスクID**を確認する。差分は `git diff` / `git status` や、該当の result.md（`logs/<タスクID>_*.result.md`）を起点に把握する。

### 2. 観点に沿って確認する

上の「何と照らすか」を順に当てる。特に見るべき頻出ポイント:

- 仕様の取りこぼし・誤り（rule.md の意味論との差）
- 層の依存方向の逸脱、純粋性（domain の副作用）違反
- 決定性の破れ（非注入の乱数、順序非決定なイテレーション）
- 完了条件・テストの不足、カバレッジ低下、境界/コーナーケース未テスト
- 「簡易実装」「保留」とされた箇所が、後続 Phase の前提を壊していないか

### 3. 指摘をまとめる

- **重大度で分ける**（例: 必須修正 / 望ましい改善 / 軽微・好み）。各指摘は「該当箇所（file:line）/ 何が問題か / なぜ問題か（どの正典に反するか）/ 提案」を簡潔に。
- 良い点・問題なしの確認も書く（過剰な指摘で implement を萎縮させない）。
- 設計と実装の**乖離**は、design.md / todos.md の更新が要る形で切り出し、`its-consolidate` に渡せるようにする。
- 仕様判断が要る論点が出たら `tbd.md` への追加を提案する。

### 4. 作業記録を残す

タスクIDがあれば `logs/<タスクID>_<slug>.result.md` に記録する（共通規約は `its-design` の SKILL.md 末尾参照）。
冒頭に実施日時・使用モデル、本文に対象・観点・重大度別の指摘・乖離の引き継ぎを書く。

## サブエージェント運用（任意）

広範囲を見る場合、読み取り専用の探索サブエージェント（Explore 等）で対象差分や該当ファイルを洗い出してから本体で判断すると効率的。ユーザーが明示的に求めた場合のみエージェントを起動する。
