### 主要な設計判断（decisions.md）

- TypeScript + Vite、UIフレームワークなし（素のTS+DOM）、マップ描画は Canvas 2D。
- クリーンアーキテクチャ 4層（domain / application=サービス層 / infrastructure / presentation）、依存は内向き。
- 六角座標は pointy-top の axial(+cube)。hex数式はサブエージェントが数値検証し正確と確認。
- 決定的乱数（SeededRng）を全面採用、GameState はシリアライズ可能な純データ。
- ローカル本番相当確認は Apache(httpd:2.4) コンテナで実施。

## サブエージェントレビューと反映

general-purpose エージェントで批判的レビューを実施。hex 数式（axial/cube・近傍・距離・hex↔pixel往復）は
**数値検証の結果すべて正確**と確認された。指摘のうち妥当なものを以下のとおり反映した。

### MUST（反映済み）

- **M-1**: ルールの正典 `docs/rule.md` が空 → MVPルールを正典として新規作成。design.md は rule.md を参照。
- **M-2**: 勝敗判定の優先順位が未定義 → 「プレイヤー相でゴール到達は即勝利・敵相スキップ／競合時は勝利優先」を
  rule.md §4.1・design.md §6/§10 に明記。
- **M-3**: 戦闘発生トリガの矛盾 → 「敵タイルへ移動不可・隣接時のみ AttackUnit、敵相も対称」に統一。
- **M-4**: ターン経済の曖昧さ＋状態保持不足 → GameState に `turnState`（残移動力/行動済み）を追加し、
  「移動以外の行動はそのユニットのターンを終了」と明文化。
- **M-5**: イベント配信の二重化 → 「全イベントは subscribe に一本化、dispatch は成否/理由のみ」を D-09 として確定。

## 追加指示 (2026-06-21): todos.md の実装可能性向上

### 指示概要

- AGENTS.md に追記された開発ポリシー（§「AIエージェントの使い分け…」）に基づき、**軽量モデル（Haiku 等）が
  早期停止せず implement できるよう todos.md を詳細化**する。最大の懸念は「指示者でも曖昧な点を Haiku が
  実装できるか」。design.md の全体感には変更不要。必要なら Haiku サブエージェントで詳細度を検証してよい。

### 方針と成果物

- 早期停止リスクが高い「hex 数学」「共有型の一貫性」は各タスクに散らすと重複・ドリフトを招くため、
  **共有参照ドキュメント2点を新設**し todos.md から参照させた:
  - `docs/hex-reference.md`: hex 式の正典（axial/cube・近傍固定index・距離・cube丸め・pixel変換・座標キー・
    **hex直線(line/lerp)**・ユニットテスト一覧・数値例）。
  - `docs/types-reference.md`: 型・定数の正典（Tile/GameMap=`Record`・Unit/Nest・GameState・Command/Event・
    `CommandResult`/`RejectReason`・SeededRng/StoragePort・数値定数・**共有ヘルパ minBy/occupantAt/sampleN/
    GenResult**）。
- `todos.md` を全面詳細化: 各タスクに **対象 / API（シグネチャ）/ 要点（擬似コード）/ テスト / 完了条件 / 参照**
  を付与。冒頭に「読み方（早期停止ポリシー・共有前提・決定性規律）」を追加。型・式は参照ドキュメントを指し重複回避。
- `design.md` を最小限修正: §5.1 に hex-reference、§5.2 に types-reference へのポインタ追加。
  シリアライズ可能性（D-08）に合わせ **`GameMap` を `Map`→`Record<CoordKey,Tile>` に確定**。
- `docs/rule.md §5` に「**1タイル1ユニット**（敵味方問わず）」の衝突ルールを明記。

### Haiku サブエージェントによる実装可能性検証と反映

AGENTS.md L65-67 の推奨どおり、Haiku モデルのサブエージェントに「implement 担当として早期停止ポリシーで
読み、曖昧点・矛盾・実装不能点を報告せよ」と指示（実ソースは作成させない）。結果:

- **hex 数式は3つの数値例まで手計算で照合され一致**。Phase 1/4/7/8 は「実装可能」判定。
- Phase 2/3 にブロッキング級の曖昧点6件・推奨6件を指摘。**妥当なものをすべて反映**:
  - **B-01** `minBy` 未定義 → types-reference §6 に挙動定義（タプル辞書順・id 昇順の意味）。
  - **B-02** 敵同士の衝突可否 → rule.md §5 に「1タイル1ユニット」、`occupantAt` を定義し敵AIで使用。
  - **B-03** `carveCorridor` の hex 直線の刻み → hex-reference §8 に `hexLine`（cube lerp, サンプル数 n+1）を追加。
  - **B-04** `sampleN` 未定義 → MapGenerator タスクに Fisher-Yates 擬似コード（rng のみ・決定的）を明記。
  - **B-05** 敵死亡時の配列操作 → 「id 列をループ前に確定し都度生存確認」「除去は filter で新配列」を規約化。
  - **B-06** `GenResult`/`attempt` の戻り値型 → types-reference §6 で型確定、タスクで `attempt(): GenResult` 明記。
  - **M-01** 敵AIテストの盤面を座標で具体化 / **M-02** 境界丸めの具体値を hex-reference §7 に追加 /
    **M-03** 決定性テストを `JSON.stringify` 一致と定義 / **M-04** 敵相では勝利判定しない旨を明記 /
    **M-05** `turnState` は毎ターン player/robot から再構築（敵削除処理不要）/ **M-06** BuildRobot に G-02
    確認待ちの注記を追加。
