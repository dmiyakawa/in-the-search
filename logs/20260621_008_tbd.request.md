以下で tbd.md に現時点で存在する要決定ポイントの一部に回答しますので、指針に従って関係するファイルに決定で影響を受ける部分を更新してください

## T-01: UIフレームワークの採否

必要に応じて導入を検討するのは問題ありません。
必要とする具体的な状況に応じてフレームワークを判断して選択してください。
一応「好み」のレベルで意見を述べます

- ゲームであるため関係がない可能性が高いですが、もし「Webフレームワーク」を活用するのだとすれば Vue.js がよく、ついで preact / React (SPA) と続きます
- Web Componentの利活用を促す軽量フレームワークではさらに土地勘がありませんが、若干Litの方が望ましいと感じます
- いずれのフレームワークでもユニットテスト・結合テスト・E2Eテストや総合テストといった結合度の濃淡に併せた多層のテストを実施して頑強にするというアプローチを重視してください

## T-02: マップ描画方式（Canvas 2D / SVG）

アニメーションのスムーズさは魅力的です。Canvas 2Dをまず検討すべきです。

なお、このゲームでは敵とロボット数が増大した際に一度に行う計算と描画が大きくなる可能性についてはうっすら懸念しています。
ただ、MVPレベルでは全く問題にならないのも理解できます。

1ターンごとの描画負荷が上がった際にどうするべきかについていつか検討すべき旨はどこかで判断すべきで、別途そのことを tbd.md に書くべきかもしれません
WebGL等何か選択肢があるかと思いますが、その際に描画がボトルネックなのか計算がボトルネックなのかでも判断が揺らぎそうな憶測があります。

## G-02: プレイヤー本体 vs 脱出ポッド/ロボットの関係

暫定案に修正を加えます。

- プレイヤー本体は移動ユニットのみで、脱出ポッドは開始タイルの固定拠点です
- プレイヤーはポッドに重なることができます
    - 「1タイルには最大1ユニットしか存在できない」というルールと衝突しない設計が必要です。場合によってはこの「ユニット」の解釈を工夫する必要があります
    - なお、マップの固定建造物（ゴールもその一つ、その他クエストでは登場しがち）にはプレイヤーと敵は重なれるケースが多々発生するはずです
- プレイヤーはスタート時にはポッド上もしくは近傍からスタートします
- ロボットの建造はポッドタイル上のプレイヤー本体のみが行えます
- ポッド自身はHPと防御に関する数値は持てますが、ロボットのような能動的な操作を行う想定はありません
    - 動作しないロボットとみなすことは問題ありませんが、プレイヤーと重なれることは必須になります
- 敗北条件は「プレイヤー本体の死亡」「ポッドの破壊」のいずれかです
    - 重なっている場合に攻撃を受けると、プレイヤーのHPではなくポッドのHPが減ります
- 敵は視界に入ったポッド・プレイヤー両方を攻撃し得ます
    - プレイヤーを優先します

## ゲームの予見可能ポリシー

MVP以降しばらくの間の意思決定を記述していきます。
まず、G-03の前に予見可能ポリシーを記述します
（この言葉は独自ですが、Slay the Spire等のターン制戦闘と類似した考え方です）

あるターンでプレイヤーが行動を計画して確定させる前にそのターンの敵や他のロボットの動作がどうなるかは100%予見出来るようにします。
敵の行動や巣からの敵の生成などのイベントでも同様です。
プレイヤーの位置に応じて相手の行動が変わるときには確定前にその行動をUI上から確認出来るのが望ましいです
（例えば薄い配色で移動先が分かる、ダメージを受けるならダメージも予想できる、という具合です）

これは一見してランダムと思われる挙動をしてはいけないということではなく、
ユーザーの決定が同じならば、開始から終わりまで動きは決定的であり、かつ、ターン毎のユーザーの決定後は正確に確認できるということです。

なお、ゲームのシードをただ単一とすればよいわけではなく、そのシードから得られる乱数の使い方には工夫がいる可能性があります。
現時点で存在しませんが、ゲーム内のイベントにおいては次のような動作が望ましいです：

> イベント：謎のほこら ... プレイヤーはHPを一定失い、ランダムなプラスの効果の一つを得る。効果は有限で選べないが、いつ実行してもそのゲーム内での結果は同じである

## G-03: 戦闘システムの詳細

自分自身やロボット、敵をユニットとしたとき、ユニットには HP / 視界 / 移動力 / 攻撃 が与えられます。
加えて、攻撃の種類も追加します
何も指定がなければMVP時点で「近接」としてよいですが、脱出ポッド ≒ 自基地は少しだけ異なる想定が現時点でもあります

- プレイヤー ... 近接
- 脱出ポッドに重なっているプレイヤー ... 範囲2までの距離に対応できる（敵への対応力の向上）

ロボットの性質が未議論ですが、ロボットでも近接攻撃、遠隔攻撃はありえます。
また「Xターン後、対象範囲（半径）に所定のダメージ」といった程度の予見可能かつ将来にわたる動作というものはありえます。

当座暫定案で問題ありません。敢えて言えば、特にルールの追加がない限りはプレイヤー > 基地 > ロボットの順で攻撃優先度があります。
（やはり現時点で存在しませんが、この優先度を上書きする存在は将来ありえます。例えばロボットの中で敵を誘導するデコイといった存在は将来あり得るかもしれません）

## G-07: ターン経済（行動力・複数ユニット操作）

特にロボットの操作について、
ロボットはその目的に応じて「待機」「実行中」の状態があり得、実行中は有限のパターンで固定的で簡潔なアルゴリズムを想定します。
選択できるアルゴリズムはロボットによって決まっています。

例を挙げます。

- 指定された地点に最短経路（に見える方法で）移動する
- 視界に入った敵に近づいて攻撃する
- 視界に入った敵に砲撃する（遠隔攻撃）
- 敵から逃げる

「実行中」を「待機」に出来るかどうか自体もロボットの性能になるため、必ず固定とはならないことに注意します。
例えば仮想例ですが、ゲーム開始初期のロボットでは近接攻撃を無効化できず、延々壊れるまで敵対行動を取るが、後半で移動を指示できる、逃げることも指示できる、という具合です

## G-08: 敗北/終了条件の追加要素

現時点では前述のとおり「プレイヤー本体の死亡」「ポッドの破壊」のいずれかが満たされたら敗北です。

クリア条件はMVPでは「ロケットに到達」で良く、前述の通りこのあと修理ミッションのような複数の必須クエストが続きます。
クリア条件とそれを満たすためのクエストが1つ以上ある、というモデリングは現時点でも妥当に見えます。

## G-10: セーブ/ロード・難易度・シード共有

難易度は現時点では後回しで問題ありません
開発時には少数の難易度を設定すると言うよりも各種のパラメータをいじって開始できる柔軟性のほうが求められます。

他のセーブ・ロード・シード共有についてはMVP後に一考の価値があります。
シード共有については開発時にはその開発バージョン以外で再現性を保持する必要はありません。
